# Forms (Feedback Project 3) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Linear's issue templates in the API, and forms built on them that people outside the workspace fill in on a link (confirmed by email) or on portal boards (signed in), each submission becoming an issue plus feedback.

**Architecture:** Task 1 implements Linear's `Template` (issue type, form fields in `templateData`). Task 2 adds form settings, the submission core that turns answers into an issue and feedback, and the board-of-origin rule. Task 3 adds the public form routes inside the portal's routes. Tasks 4–5 build the web: the form editor in Settings, then the public form pages and board integration with the smoke check.

**Tech Stack:** Bun, Elysia, Drizzle, graphql-yoga (Linear's SDL, never edited), better-auth instance plugin, the portal routes and session (`apps/api/src/portal`); Next.js 15, React 19, TanStack Query 5, gql.tada; `bun test`.

**Spec:** `docs/superpowers/specs/2026-11-24-forms-design.md`

## Global Constraints

- Linear's SDL is never edited; `gql.tada check` passes. Incremental migrations (next is 0052).
- Only template type `issue`; others → INVALID_INPUT.
- A form = a team template with a `form_settings` row; only owners and admins change or delete it (also through GraphQL); a form's team must be public, checked on every request.
- Link submissions create nothing until the email is confirmed; signed-in portal visitors submit at once; on a board, submitting needs portal sign-in.
- Answers up to 10,000 characters each; options only from the form; required questions enforced.
- The form page answers the same for allowed, blocked or rate-limited addresses ("Check your email to confirm your request").
- Form issues: webhooks, workflows and new-issue notifications run; `Issue.externalUserCreator` = requester; feedback source `form`, attachment subtitle "Form: <form name>".
- Commit per task, no trailer. Questions settled the way Linear does.

## Review Focus

1. A confirmation link opened twice, after 24 hours, after the form was deleted or its team made private, or by a requester blocked after submitting: one issue at most; refused cleanly otherwise; no requester created for a refused one. Test in Task 3.
2. A member editing a form's template through `templateUpdate` / `templateDelete`, or moving it to a private team: FORBIDDEN for members; admins allowed, and a private team hides the form. Test in Task 1 / Task 2.
3. Option labels / priority that were deleted or moved after the form was saved (a label deleted, a state deleted): the submission still creates the issue with what remains valid, never a 500. Test in Task 2.
4. A form placed on a project board whose project no longer includes the form's team, or a board whose access changes: the form is hidden there, a submission through that board refused. Test in Task 3.
5. Answers carrying Markdown or HTML (headings, links, `<script>`), and a title answer of 300 characters: description keeps them as text in the answer block, title cut to 255. Test in Task 2.

### Task 3: Public form routes

**Files:**
- Modify: schema + migration 0054: `form_submission` (id, token_hash unique, template_id references template on delete cascade, email lowercased, name, answers jsonb, expires_at = 24 h, used_at, created_at).
- Create: `apps/api/src/forms/public.ts`
- Modify: `apps/api/src/portal/routes.ts` (form routes), `apps/api/src/portal/rate-limit.ts` (`LIMITS.formSubmissions`), the worker or an existing purge (delete expired `form_submission` rows), `apps/api/AGENTS.md`
- Test: `apps/api/src/forms/__tests__/integration/public.test.ts`

**Interfaces:**
- Consumes: Task 2; portal `visitorFromRequest`, `allow`, `LIMITS`, the sign-in mail sender and session creation from `portal/session.ts` (extract a `startSession(requesterId, email): Promise<string>` there if confirm-sign-in has none).
- Produces routes:
  - `GET /portal/forms/:slug` → `{ name, intro, fields: FormField[] (options without labelId / priority), visitor }` when the link is on; 404 otherwise.
  - `POST /portal/forms/:slug { answers, email?, name? }`: signed in → `submitForm` at once → `{ status: 'created', identifier }`; signed out → validates, then always `{ status: 'pending' }`; stores a `form_submission` and mails `${APP_URL}/forms/<slug>/confirm?token=` (in the background, like portal links) only when the address is not blocked and within `LIMITS` (link limit per address, `formSubmissions` per client address 20 / hour); name required for a new requester's address (checked at confirm: the submission keeps the given name).
  - `GET /portal/forms/confirm-info?token` → `{ formName }` or 400 invalid / expired / used; `POST /portal/forms/confirm { token }` → claims the row in one conditional UPDATE, resolves or creates the requester (project 1 rules, name from the submission), refuses a blocked requester with 400 "link no longer valid", re-reads the form (`getFormBySlug`, 400 when gone or private), `submitForm` with origin board null, starts a portal session (sets the cookie) → `{ identifier, boards: { slug, name }[] }` (boards showing the issue).
  - `GET /portal/boards/:slug/forms` → forms placed on the board that the visitor can read (board readable, form's team public, placement still valid) as `{ slug, name, intro, fields }[]`; `POST /portal/boards/:slug/forms/:formSlug { answers }` → signed in only (401 otherwise), `submitForm` with origin `{ boardId, projectId: board.projectId }`, rate-limited as suggestions; 404 when the form is not on the board.
