# Sorting Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every `sort` argument in Linear's schema works with correct forward paging,
and the app's issue lists gain Linear's missing orderings; the initiatives list becomes
a sortable table.

**Architecture:** One shared sorted-pagination helper in `graphql/sort.ts` takes a list
of typed sort keys (each an SQL expression with direction and null placement) plus the
tie-break chain and builds ORDER BY and a keyset cursor. Each list maps Linear's sort
input to those keys. The web extends its in-browser issue comparator with the same
rules.

**Tech Stack:** Bun, graphql-yoga with Linear's vendored SDL, Drizzle/Postgres, Next.js
15, gql.tada.

**Spec:** `docs/superpowers/specs/2026-11-25-sorting-design.md`

## Global Constraints

- Linear's SDL is never edited; `gql.tada check` passes. No migration unless an index is needed (then one incremental migration).
- Keys follow the SDL descriptions: cycle by start date (`currentCycleFirst`), project by name, milestone by target date, release by most recent release date, customer by name, customer revenue by revenue.
- Multi-valued keys (label, labelGroup, customer, customerRevenue, release): ascending uses the lowest value, descending the highest.
- Tie-break chain for issues: manual `sortOrder` asc, `createdAt` desc, `id`; other lists: `createdAt` desc, `id`.
- `nulls` default `last`; `priority.noPriorityFirst` default false (No priority sorts after Low).
- Sorted lists page forward only; `last`/`before` with `sort` → INVALID_INPUT. `sort` wins over `orderBy`. `slaStatus` → INVALID_INPUT.
- A related item the viewer cannot see sorts as empty. While Customers is off, `customer` / `customerRevenue` sort as empty and `customerCount` counts people.
- Follow `AGENTS.md`, `apps/api/AGENTS.md`, `apps/web/AGENTS.md`, DESIGN.md. Commits: one per task, no trailer or metadata.

## Review Focus

1. **Paging through a sort with many equal values** (e.g. 120 issues all priority High, `first: 50`) returns 120 distinct issues over three pages. Test in Task 1 and Task 2.
2. **Nulls with `nulls: first` descending** (due date) put empty values first and page correctly across the null/non-null boundary. Test in Task 2.
3. **Sorting issues by project, cycle or milestone when that item belongs to a private team the viewer is not in** sorts it as empty and reveals nothing about it. Test in Task 2.
4. **Two sort keys** (`[{ priority: { order: Ascending } }, { dueDate: { order: Descending } }]`) apply in order. Test in Task 2.
5. **The app and the API agree** for each new ordering on the same fixture. Test in Task 4 (same fixture values as Task 2's tests, compared to the expected order list).

### Task 1: Shared sorted pagination

**Files:**
- Create: `apps/api/src/graphql/sort.ts`, `apps/api/src/graphql/__tests__/integration/sort-users.test.ts`
- Modify: `apps/api/src/graphql/connection.ts` (export what `sort.ts` needs), the users resolver (`resolvers/user.ts` `users` / `Team.members` where the SDL has `sort`)

**Interfaces:**
- Produces:
  - `type SortKey = { sql: SQL; order: 'asc' | 'desc'; nulls: 'first' | 'last'; type: 'number' | 'text' | 'date' | 'uuid' }`.
  - `parseSortInput<K extends string>(input: unknown, keys: Record<K, (opts: Record<string, unknown>) => SortKey>, path: string): SortKey[]` — a list of one-key objects in order; unknown keys or two keys in one object → INVALID_INPUT; `order` `Ascending|Descending` (Linear's `PaginationSortOrder`), `nulls` `first|last`.
  - `paginateSorted<Row extends { id: string }, T>(args: PageArgs, keys: SortKey[], tieBreak: SortKey[], load: (where: SQL | undefined, orderBy: SQL[], limit: number, selectExtra: SQL[]) => Promise<Row & { __sort: unknown[] }>[]>, map: (r: Row) => T): Promise<Connection<T>>` — forward only; cursor = base64 JSON of the row's sort values + id; `after` builds the lexicographic keyset condition honouring each key's direction and null placement; `last`/`before` → INVALID_INPUT.
  - Users sort: `displayName`, `name` (`UserSortInput`).
- [ ] **Step 1: Write the failing tests** (`sort-users.test.ts`): `users(sort: [{ name: { order: Ascending } }])` orders by name; descending reverses; 7 users with the same name page with `first: 3` into 3+3+1 distinct ids (Review Focus 1 shape); `last: 2` with sort → INVALID_INPUT; `sort: [{ bogus: {} }]` → INVALID_INPUT.
- [ ] **Step 2: Run** `cd apps/api && bun run test src/graphql/__tests__/integration/sort-users.test.ts` — Expected: FAIL.
- [ ] **Step 3: Implement** `sort.ts` and the users sort.
