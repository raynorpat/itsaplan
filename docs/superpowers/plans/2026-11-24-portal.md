# Portal (Feedback Project 2) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Workspace boards at `/portal/<slug>` where people outside the workspace sign in by emailed link, vote, comment and suggest, stored as project 1 feedback, Linear comments and issues.

**Architecture:** Tasks 1–4 build the API: boards and their issue query, visitor sign-in with its own session, votes and suggestions, comments. Its own Elysia routes under `/portal/*` accept only the portal session; admin endpoints live in the instance plugin. Tasks 5–6 build the web: the workspace side (settings, issue page) and the portal pages.

**Tech Stack:** Bun, Elysia, Drizzle, graphql-yoga (Linear's SDL, never edited), better-auth instance plugin, `@repo/auth` `sendAuthEmail`; Next.js 15, React 19, TanStack Query 5, gql.tada; `bun test`.

**Spec:** `docs/superpowers/specs/2026-11-24-portal-design.md`

## Global Constraints

- Linear's SDL is never edited; `gql.tada check` passes. Incremental migrations (next is 0049).
- Portal routes (`/portal/*`) accept only the portal session cookie; a better-auth session or API key there is ignored (treated as signed out). The portal cookie is never accepted by `/graphql`, MCP, `/api/auth/*` or any other route.
- Access to a restricted board is checked on every request (domain list, email list, board enabled, requester not blocked).
- Private-team issues are never shown on a board; a board cannot target a private team.
- Public status: backlog / unstarted / triage → `planned`, started → `inProgress`, completed (within 30 days of `completedAt`) → `done`; canceled and older completed issues are not shown.
- Visitors never see emails; they see `displayName` and avatar. Guests in the workspace see no requester on comments or issues (`Comment.externalUser`, `Issue.externalUserCreator` null).
- Votes: no notification; suggestions and visitor comments: normal issue / comment events, workflows and notifications.
- Commit per task, no trailer. Questions settled the way Linear does.

## Review Focus

1. A visitor signed in for restricted board A requests board B (public), board C (restricted, other domain), and a board whose domain was removed after sign-in: B and A readable until the removal, C refused with 404, no data from C. Test in Task 2.
2. A board on a project that contains a private team's issue, and an issue moved from a public to a private team after it was voted on: neither listed, detail 404, vote refused. Test in Task 1 / Task 3.
3. Portal thread of restricted board A on an issue also shown on public board B with "All comments": B does not show A's thread. Test in Task 4.
4. The same visitor voting twice concurrently, and unvoting when the team also logged feedback for them: one portal vote, count unchanged by the team item, unvote removes only the portal item. Test in Task 3.
5. A sign-in link opened twice, expired, or for a blocked requester; a confirm without a name for a new address: refused / asks for the name, never creates two requesters for one email. Test in Task 2.

### Task 3: Board reading, votes and suggestions

**Files:**
- Create: `apps/api/src/portal/issues.ts`, `apps/api/src/portal/votes.ts`, `apps/api/src/portal/suggestions.ts`
- Modify: `apps/api/src/portal/routes.ts`, `apps/api/src/issues/store.ts` (`createIssue` accepts `externalUserCreatorId`), `apps/api/src/graphql/resolvers/issue.ts` (`Issue.externalUserCreator`, null for guests)
- Test: `apps/api/src/portal/__tests__/integration/board-actions.test.ts`

**Interfaces:**
- Consumes: Tasks 1–2; project 1 `createRequesterAttachment(issueId, requesterId, 'portal', null)`, `createNeed`, `deleteNeed`, `requesterCountSql`.
- Produces routes (all 404 for a missing / disabled board or one the visitor cannot read; issue routes 404 when the board does not show the issue):
  - `GET /portal/boards/:slug` → `{ name, intro, access, comments, suggestionsEnabled, showDescription, canRead, visitor }` (`canRead` false on a restricted board shows the sign-in page; nothing else returned).
  - `GET /portal/boards/:slug/issues?sort=top|new&q=` → `{ issues: PortalIssue[] }`, `type PortalIssue = { identifier, title, status: PublicStatus, votes: number, comments: number, voted: boolean, underReview: boolean }`; the signed-in visitor's own suggestions not on the board are included with `underReview: true` and `status` `planned`.
  - `GET /portal/boards/:slug/issues/:identifier` → `PortalIssue & { description: string | null }` (description only when `showDescription`).
  - `POST` / `DELETE /portal/boards/:slug/issues/:identifier/vote` → `{ voted, votes }`. A vote is a `CustomerNeed` with a `portal` attachment and null body; at most one per requester per issue (serialize with a `FOR UPDATE` lock on the requester row); `voted` is true when the requester has any active feedback on the issue; DELETE removes only portal-sourced needs without a body.
  - `GET /portal/boards/:slug/similar?q=` → up to 5 `PortalIssue` on the board whose title matches the words of `q` (ILIKE on each word, ordered by votes).
  - `POST /portal/boards/:slug/suggestions { title (1–255), details (≤ 10,000) }` → `{ identifier }`; 403 when suggestions are off; creates the issue in the board's suggestion team / state / label with `externalUserCreatorId` and no member creator, then a portal need with body = details.
