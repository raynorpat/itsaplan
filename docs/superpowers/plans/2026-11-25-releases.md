# Release Tracking Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Linear's release tracking: pipelines with stages, releases with issues, links,
documents and release notes, CI sync through access keys, and "Shipped in <release>"
updates to requesters.

**Architecture:** A `releases/` API folder (pipelines, stages, releases, issue links,
notes, sync, access keys) behind Linear's GraphQL operations and instance endpoints for
access keys. The `*ByAccessKey` mutations authenticate a pipeline access key in
`graphql/context.ts`. Requester updates gain a `shipped` change kind. The web gets a
shared releases service and a `releases` feature with pipeline, release and settings
pages.

**Tech Stack:** Bun, Elysia, graphql-yoga with Linear's vendored SDL, Drizzle/Postgres,
better-auth instance plugin, Next.js 15, React 19, TanStack Query, gql.tada.

**Spec:** `docs/superpowers/specs/2026-11-25-releases-design.md`

## Global Constraints

- Linear's SDL is never edited; `gql.tada check` passes. One migration `0064_*` in Task 1; a later task that needs a column adds it with its own migration only if unavoidable.
- Follow `AGENTS.md`, `apps/api/AGENTS.md`, `apps/web/AGENTS.md`, `packages/auth/AGENTS.md`, DESIGN.md; web features never import each other.
- Pipelines: visible to whoever sees one of their teams; created and edited by owners, admins and members of their teams; guests read their teams' pipelines only.
- Default stages per pipeline: Planned (`planned`), In progress (`started`), Completed (`completed`), Canceled (`canceled`).
- Continuous version default: first 7 characters of the commit SHA; a repeated version needs the same full SHA (else INVALID_INPUT).
- Access keys: workspace owners and admins create and revoke; shown once; stored as SHA-256; prefix `itpr_`; act only on their pipeline and only in `releaseSyncByAccessKey`, `releaseUpdateByPipelineByAccessKey`, `releaseCompleteByAccessKey`, `recentReleasesByAccessKey` (if in the SDL).
- An issue ships when it is in a release, the release is completed and the issue is completed, at the latest of the three; only production pipelines; once per person, issue and release.
- No release webhooks. Pull request references are skipped. Path patterns are stored, not applied.
- Commits: one per task, Conventional Commit subject, no trailer or metadata.

## Review Focus

1. **A sync mentioning an issue of a team outside the pipeline, an archived issue, a lowercase identifier (`eng-12`) or an unknown one** — outside / archived / unknown are skipped and listed as skipped; lowercase matches. Test in Task 3.
2. **The same continuous sync run twice** (CI retry) creates one release and does not duplicate issue links. Test in Task 3.
3. **An access key used for anything else** (a normal query, another pipeline, after revoke) is refused with AUTHENTICATION_ERROR or FORBIDDEN. Test in Task 3.
4. **An issue completed after its release completed** ships then, once; an issue reopened and completed again does not ship twice. Test in Task 5.
5. **Completing a scheduled release with rollover** moves only unfinished issues, into the next planned release, creating "Next" when none. Test in Task 2.
